# 세션 평가 기준과 규칙 운영

Atlas는 코딩 에이전트의 **관측 기록으로 개선 후보와 다음 행동**을 제안한다. 모델·스킬을 썼다는 사실이나 반복 횟수만으로 낭비·실패를 판정하지 않는다.

## 규칙과 구현의 단일 원본

규칙 정의는 [`evaluation-catalog.ts`](../packages/contracts/src/evaluation-catalog.ts)에 둔다. 서버와 문서 생성기가 같은 ID·버전·필수 사실·적용 조건·rubric을 읽는다. 전체 규칙은 이 문서의 [평가 규칙 카탈로그](#평가-규칙-카탈로그)에 있다. 평가 원칙과 운영 설명은 직접 수정하고, `evaluation-rules:start/end` 주석 사이의 규칙 목록만 자동 생성한다. 생성기는 나머지 내용을 보존한다.

```sh
pnpm generate:evaluation-docs
pnpm check:evaluation-docs
pnpm test
```

CLI는 개발 중 문서 생성·드리프트 검사를 위한 도구다. 실제 평가는 서버에서 실행한다. CI도 생성 문서가 코드와 일치하는지 검사한다.

| 단계           | 실행 위치와 책임                                                                                |
| -------------- | ----------------------------------------------------------------------------------------------- |
| 수집           | Codex·Claude Code 원본을 공통 이벤트로 정규화. 관측된 모델·도구 상태·스킬 참조만 기록           |
| 사실 계산      | 서버가 횟수·토큰·구조화된 결과를 계산. 문자열 `error`는 실패로 세지 않음                        |
| 적용 규칙 선택 | 필수 사실이 없으면 `insufficient`, 대상이 아니면 `not_applicable`. 최대 3개 의미 기반 규칙 그룹 |
| AI 설명        | 선택된 rubric과 제한된 근거를 입력. 문제·즉시 할 일·검증 기준·규칙 버전·근거 ID 반환            |
| 결과 검증      | JSON 구조·필수 필드·실제 입력에 포함된 근거 ID·허용한 규칙 ID/버전 검사                         |
| 결과 재사용    | 동일 세션 revision·평가 버전·설정의 완료 결과가 있으면 재사용. 강제 재분석은 새 결과 생성       |

프롬프트의 공통 지침·출력 계약·선택 rubric은 앞에, 세션별 근거는 뒤에 둔다. 모든 규칙을 매번 넣거나 규칙마다 따로 AI를 호출하지 않는다. 제공자 프롬프트 캐시의 활성 여부·절감 효과는 아직 검증하지 않았다.

## 사실과 판단의 경계

| 상태                       | 뜻                                  | 예시                                                  |
| -------------------------- | ----------------------------------- | ----------------------------------------------------- |
| `observed`                 | 원본의 구조화된 필드나 직접 기록    | 실행 모델 ID, 도구 종료 코드                          |
| `unknown` / `insufficient` | 값이 없거나 판단에 필요한 맥락 부족 | 실행 모델 미수집, 스킬 효과 비교군 없음               |
| `candidate`                | 검토할 이유가 있는 관측             | 동일 명령 세 번. 필수 검증·변경 뒤 재실행일 수도 있음 |

**실행 모델(subject)**은 사용자의 코딩 작업을 수행한 모델이다. **평가 모델(judge)**은 Atlas에서 이 기록을 분석한 모델이다. 둘의 제공자·모델 필드를 분리한다. 여러 실행 모델이 관측됐는데 턴별 귀속이 충분하지 않으면 하나의 모델로 단정하지 않는다.

`tool-error@2`는 구조화된 실패 또는 실제 0이 아닌 종료 코드만 사용한다. 결과가 수집되지 않으면 오류 0건으로 대체하지 않는다. `toolOutcomesObserved`로 관측 범위를 남긴다. 과거 `tool-error@1` 결과는 키워드 관측이므로 같은 의미로 비교하지 않는다.

## 현재 수집 범위와 제한

| 항목                             | 지원 범위                                          | 남은 한계                                                            |
| -------------------------------- | -------------------------------------------------- | -------------------------------------------------------------------- |
| 사용자 지시·도구 호출·결과       | 공통 이벤트, 호출 ID, 시각                         | 축약·마스킹·누락된 맥락은 복원할 수 없음                             |
| 실행 모델                        | v2의 `subject_model`, 관측된 모델·제공자·추론 설정 | 원본에 없는 제공자·가격·버전은 추측하지 않음                         |
| 스킬                             | 명시적 호출·관측 참조가 있을 때만 기록             | 이름 언급은 실행 아님. 스킬 전체 본문·비밀 지시는 기본 수집하지 않음 |
| 이미지                           | SHA-256·MIME·크기·해상도·발생 위치                 | 이미지 픽셀·OCR·화면 내용 평가 없음                                  |
| 도구 성공·실패                   | 구조화된 상태·종료 코드가 있는 경우                | 결과 텍스트에만 상태가 있으면 보수적으로 unknown                     |
| 완료·검증 간 변경 여부·스킬 효과 | 신뢰 가능한 구조화 사실이 필요                     | 일반 세션에서 아직 충분히 추출하지 못하면 해당 rubric을 보류         |

AI 입력은 최대 64개 발췌·32,000자다. 지시·관측 메타데이터·스킬 관련 호출·결과·시간 분산을 우선하고 선택·축약 범위를 기록한다. 이는 전체 세션의 의미를 보장하는 계층적 증류가 아니다. ID가 존재한다는 검증과 **그 근거가 결론을 뒷받침한다는 검증은 다르다.**

## 결과를 행동으로 연결

주 화면은 문제와 해결 방법·검증 기준을 비교한다. 근거는 버튼으로 여는 상세창에서 사람이 읽는 발췌를 먼저 보여주고, 원시 JSON은 펼쳐 확인한다.

- 새 결과는 마스킹된 정규화 이벤트의 SHA-256을 남긴다. 과거 결과는 저장된 발췌의 해시임을 구분한다.
- 에이전트 작업 지시 복사는 세션·결과·규칙·근거 참조와 완료 기준을 포함한다. 복사만 하며 자동으로 외부 에이전트를 실행하지 않는다.
- 수정 후 재분석으로 새 결과를 만들 수 있다. 개선안 적용 이력과 전후 효과를 자동 추적하는 기능은 아직 없다.
- 상세 근거·전체 결과는 최초 접수부터 7일, 원문 없는 요약은 30일만 보관한다. 해시는 원문을 대신하거나 진실성을 보증하지 않는다.

## 모델·스킬 비교 원칙

고성능 모델도 위험·복구·불확실성 때문에 적절할 수 있다. 모델 적합성 rubric은 작업 조건과 실제 모델을 연결하고, 비교군이 없으면 낮은 설정의 A/B 검증을 제안하는 수준으로 제한한다. 가격·과금 조건 없이 절감액을 계산하지 않는다.

스킬 효과는 모델·작업·지시 버전과 함께 비교한다. 파일 해시만으로 의미·충돌을 판단할 수 없으며, 같은 완료 기준의 전후·교차 A/B가 없으면 인과 효과를 주장하지 않는다. 관측에 없는 작업 복잡도·위험·완료 상태를 코드가 임의 분류하지 않는다.

## 규칙을 갱신하는 방법

`draft → calibrating → active → deprecated → retired` 상태를 사용한다. 규칙 변경은 카탈로그·반례 fixture·생성 문서를 함께 수정한다. 입력·적용 조건·rubric이 바뀌면 버전을 올린다. 이미 저장한 결과는 당시 버전을 유지한다.

합성 검증은 오류 단어가 있는 성공 출력, 정상 재검증, 단순 스킬 언급, 모델 변경, 누락 근거, 잘못된 인용을 포함한다. 의미 기반 규칙은 조건부 검토 후보이며 실세션별 정확도가 보장된 점수 모델이 아니다. 실증에서 오탐·누락·보류 사유를 검토한 뒤 적용 범위를 조정한다.

모델·harness·스킬·가격이 바뀌거나 분기별로 규칙을 재검토한다. 성공 사례만 비교하지 않고 실패·중단·제외 이유도 남긴다.

## 평가 규칙 카탈로그

이 절은 `evaluation-catalog.ts`에서 자동 생성한다. 규칙 변경은 코드에 반영한 뒤 문서를 다시 생성한다.

### 공통 원칙

- 원본 이벤트와 구조화된 관측 사실만 사용한다. 누락값은 추측하지 않는다.
- candidate는 위반·낭비·잘못이라는 판정이 아니다. 반례와 추가 확인 방법을 함께 적는다.
- 선택되지 않은 rubric의 결론을 대신 만들지 않는다. 근거 ID와 적용한 규칙 ID@version을 보존한다.

### 결정적 규칙

#### repeated-tool-call@1 — 동일한 도구 호출 반복

| 항목 | 값 |
| --- | --- |
| 종류 | `deterministic` |
| 상태 | `active` |
| 기본 활성화 | `true` |
| 그룹 | `execution` |
| 필요한 관측 사실 | 없음 |

적용: 같은 도구 이름과 입력이 세 번 이상 관측됐을 때만 후보를 만든다.

- 반복 횟수와 각 호출의 이벤트 ID를 보존한다.
- 재시도·필수 검증·변경 뒤 재실행일 수 있으므로, 반복만으로 불필요했다고 단정하지 않는다.

#### tool-error@2 — 확인된 도구 실패 응답 관측

| 항목 | 값 |
| --- | --- |
| 종류 | `deterministic` |
| 상태 | `active` |
| 기본 활성화 | `true` |
| 그룹 | `execution` |
| 필요한 관측 사실 | `toolOutcomes` |

적용: 구조화된 실패 상태 또는 실제 0이 아닌 종료 코드가 관측된 결과만 후보로 만든다.

- 결과 텍스트의 error·failed·오류·실패 단어는 실패의 근거가 아니다.
- 성공 상태가 확인된 결과는 오류 단어가 포함돼도 실패 후보에 넣지 않는다.

### 의미 기반 rubric

`model-fit`은 `active`·기본 활성, `skill-impact`은 `active`·기본 활성, `verification-repetition`은 `active`·기본 활성, `premature-handoff`은 `active`·기본 활성. 필수 관측 사실·최대 그룹 수가 모두 충족된 항목만 평가 모델 입력에 넣는다. 선택되지 않은 항목은 disabled, insufficient, not_applicable 또는 deferred 이유와 함께 보존한다.

#### model-fit@1 — 실행 모델과 작업 조건의 적합성

| 항목 | 값 |
| --- | --- |
| 종류 | `semantic` |
| 상태 | `active` |
| 기본 활성화 | `true` |
| 그룹 | `model` |
| 필요한 관측 사실 | `subjectModel`, `taskContext` |

적용: 실제 실행 모델과 작업 조건이 모두 관측된 경우에만 선택한다.

- 실행 모델 ID·제공자·버전 또는 별칭·추론 강도와 작업 복잡도·위험·완료 기준을 분리해 기록한다.
- 비교군·가격·결과 근거가 없으면 더 낮은 설정이 충분했다고 말하지 않고, 필요한 A/B 비교만 제안한다.

#### skill-impact@1 — 스킬과 지시 묶음의 관측 영향

| 항목 | 값 |
| --- | --- |
| 종류 | `semantic` |
| 상태 | `active` |
| 기본 활성화 | `true` |
| 그룹 | `instruction` |
| 필요한 관측 사실 | `skillExecutions`, `instructionContext`, `outcome` |

적용: 실제 스킬 실행·적용된 지시 맥락·작업 결과가 모두 관측된 경우에만 선택한다.

- 이름 언급은 실행으로 세지 않는다. 스킬 ID·버전 또는 hash·활성화 방식·도구 결과를 근거로 남긴다.
- 동일 완료 기준의 비교군이 없으면 도움이 됨·부담됨을 결론 내리지 않고, 유지 또는 축소 A/B의 조건을 제안한다.

#### verification-repetition@1 — 검증 반복의 필요성

| 항목 | 값 |
| --- | --- |
| 종류 | `semantic` |
| 상태 | `active` |
| 기본 활성화 | `true` |
| 그룹 | `verification` |
| 필요한 관측 사실 | `verificationRuns` |

적용: 같은 대상의 반복 검증과 각 반복 사이의 변경 또는 실패 맥락이 관측된 경우에만 선택한다.

- 변경·실패 뒤 재실행, 필수 CI, 운영 확인은 중복으로 분류하지 않는다.
- 명령·대상·revision·상태와 변경 여부를 연결하지 못하면 반복의 필요성을 평가하지 않는다.

#### premature-handoff@1 — 완료 전 인계 가능성

| 항목 | 값 |
| --- | --- |
| 종류 | `semantic` |
| 상태 | `active` |
| 기본 활성화 | `true` |
| 그룹 | `completion` |
| 필요한 관측 사실 | `completion` |

적용: 요청된 완료 조건과 수행·미수행 단계 또는 차단 사유가 관측된 경우에만 선택한다.

- 완료 상태가 unknown이면 조기 인계 후보를 만들지 않고 insufficient로 남긴다.
- 사용자가 중간 리뷰를 요청했거나 외부 차단이 확인되면 조기 종료라고 단정하지 않는다.
