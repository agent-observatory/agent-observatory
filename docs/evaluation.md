# 세션 평가 기준과 규칙 운영

## 목적과 범위

Atlas는 코딩 에이전트 세션의 **관측 가능한 실행 기록**으로 개선 후보를 찾는다. 평가는 사람이나 모델의 능력·가치·구독 요금제를 판정하지 않는다. 특히 “고성능 모델을 썼다”, “스킬을 썼다”, “도구를 반복했다”만으로 낭비나 실패를 확정하지 않는다.

아래 모델·스킬 평가와 규칙 운영은 앞으로 구현할 기준이다. 현재 구현은 반복 호출·오류 키워드 규칙과 AI 설명에 한정된다.

이 문서는 두 질문을 다룬다.

1. 작업의 복잡도·위험·완료 근거에 비추어 세션의 **실행 모델** 선택을 다시 살펴볼 이유가 있는가?
2. 특정 **스킬 또는 지시 묶음**이 이 모델·작업 조건에서 도움이 되었는가, 무관했는가, 또는 부담이 되었을 가능성이 있는가?

판정은 세 단계로 표시한다.

| 상태           | 뜻                                       | 허용하는 표현                                      |
| -------------- | ---------------------------------------- | -------------------------------------------------- |
| `observed`     | 원본 이벤트나 구조화된 필드로 직접 확인  | “모델 ID가 기록됐다”, “스킬 실행 도구 호출이 있다” |
| `insufficient` | 결론에 필요한 값·맥락·결과가 없음        | “평가 불가”, “비교 기준 없음”                      |
| `candidate`    | 충분한 근거가 있을 때만 검토할 개선 후보 | “다음 비교를 권장”, “과잉 제약일 가능성”           |

`candidate`는 위반, 낭비, 잘못된 모델 선택이라는 결론이 아니다. 비용이 큰 모델도 보안·복구·불확실성·긴 맥락 때문에 적절할 수 있다.

## 대상 모델과 평가 모델을 분리한다

| 구분                        | 정의                                                                    | 현재 Atlas에서의 상태                                                                                                   |
| --------------------------- | ----------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| 실행 모델 (`subject model`) | 사용자의 코딩 세션에서 실제로 도구를 호출하고 코드를 바꾼 에이전트 모델 | Codex 어댑터 공통 이벤트에는 직접 저장하지 않는다. 현재 세션 데이터만으로 모델 ID·별칭·추론 강도·가격을 판정할 수 없다. |
| 평가 모델 (`judge model`)   | Atlas Workflow가 선택 근거와 규칙 결과를 설명하는 데 호출하는 AI        | 결과에 요청 모델과 실제 응답 모델, gateway provider, upstream provider, endpoint host, tier, 토큰 사용량을 남긴다.      |
| 결정적 규칙                 | 이벤트를 입력으로 후보를 만드는 코드                                    | 현재 `repeated-tool-call@1`, `tool-error@1`만 있다. 모델을 호출하지 않는다.                                             |

특정 모델을 Atlas 평가 모델로 선택했다는 사실은 실행 모델의 선택이 적절했다는 근거가 아니며, 반대도 성립하지 않는다. 평가 결과 화면과 데이터 계약은 두 식별자를 다른 필드로 보관·표시해야 한다.

## 현재 근거와 한계

현재 Codex 수집기는 `session_meta`에서 세션 ID·작업 경로·시작 시각을 읽고, 본문을 사용자/assistant 메시지, 도구 호출·결과, 누적 사용량 이벤트로 정규화한다. 선택 근거는 사용자 메시지 최대 14개, `SKILL.md`·`skills/`·`skill://` 텍스트가 보이는 도구 호출 최대 6개, 오류처럼 보이는 도구 결과 최대 4개와 연결 이벤트·시간 분산으로 결정적으로 고른다. 이름 언급은 스킬 실행의 증거가 아니다.

| 평가에 필요한 사실                     | 현재 지원 | 제한 또는 필요한 보강                                                                                                                                   |
| -------------------------------------- | --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 프롬프트·도구 호출·결과·이벤트 순서    | 지원      | 텍스트가 누락·마스킹·축약되면 결과 연결을 보장하지 않는다. AI 입력은 최대 64개·32,000자다.                                                              |
| 스킬 관련 도구 호출                    | 부분 지원 | 경로 패턴으로 고른 표본일 뿐, 활성화·로드·완료·버전·내용·효과를 구조화해 수집하지 않는다.                                                               |
| 실행 모델 ID·제공자·별칭·추론 강도     | 미지원    | 세션 메타데이터에 모델 관련 값이 있어도 현재 공통 계약으로 보내지 않는다.                                                                               |
| 실행 모델의 실제 비용·가격표·구독 한도 | 미지원    | 사용량 이벤트는 최신 누적 토큰만 보낸다. 토큰을 가격이나 구독 청구액으로 환산하지 않는다.                                                               |
| 작업 복잡도·위험도·성공 기준           | 미지원    | 프롬프트와 도구 출력에서 추론할 수 있을 뿐, 신뢰할 구조화 필드가 없다.                                                                                  |
| 구현·검증 결과                         | 부분 지원 | 도구 결과에 보일 수 있으나 테스트 범위·통과 여부·배포 여부를 공통 필드로 구분하지 않는다.                                                               |
| 분석 재현 정보                         | 부분 지원 | `analysisVersion`은 규칙 ID·버전과 증거 선택 전략을 담고, 작업 설정·실제 평가 모델도 결과에 있다. 평가 프롬프트 자체의 독립 버전·실행 모델 정보는 없다. |

따라서 기존 세션에서 실행 모델이나 스킬 효과를 모르면 `unknown` 또는 `insufficient`로 남긴다. 텍스트에서 추측해 채우지 않으며, 0·무료·낮은 위험으로 대체하지 않는다.

## 모델 적합성 후보

모델 적합성은 작업과 실제 실행 모델의 근거를 먼저 확인한다. 비교군이 없으면 낮은 확신의 검토 후보까지만 허용한다. 비용 정보가 없으면 비용 절감액을 계산하지 않고, 동등한 결과의 비교가 없으면 하위 모델로 충분했다고 단정하지 않는다.

| 축               | 최소 근거                                                                | 예시 분류                                                                  |
| ---------------- | ------------------------------------------------------------------------ | -------------------------------------------------------------------------- |
| 작업 복잡도      | 범위, 변경 면적, 필요한 탐색·추론·도구 단계                              | 단일 기계적 수정 / 제한된 기능 / 다중 모듈·불명확한 결함                   |
| 위험             | 되돌리기 어려움, 보안·개인정보·금전 영향, 운영 영향                      | 낮음 / 중간 / 높음. “높음”은 더 강한 모델 사용의 정당화가 될 수 있다.      |
| 완료 기준과 결과 | 요청된 산출물, 테스트·리뷰·배포 등 실제 확인된 결과                      | 완료·부분 완료·실패·미확인. 빌드 통과는 배포 성공을 뜻하지 않는다.         |
| 실행 모델 조건   | 실제 모델 ID, 제공자, 모델 버전 또는 별칭, 추론 강도, 실행 시각          | 별칭만 있으면 공급자 변경을 구별할 수 없어 비교가 약해진다.                |
| 비용·제약 맥락   | 가격 기준 시각·출처·과금 단위, 계정 한도, 지연 예산, 사용자 정책         | 값이 없으면 비용 평가는 하지 않는다. 토큰 수만으로 비용을 추정하지 않는다. |
| 비교 기준        | 같은 완료 기준에서의 더 단순한 모델·설정 또는 같은 모델의 다른 설정 결과 | 한 세션만으로 “낮은 모델이면 충분했다”를 말하지 않는다.                    |

### 후보 생성 규칙

1. 작업을 `기계적`, `제한된 변경`, `고위험 또는 불확실`, `unknown` 중 하나로 **근거와 함께** 분류한다. 자동 분류는 우선 `unknown`을 기본값으로 둔다.
2. 기계적·저위험 작업에서 상위 모델 사용이 확인되면 `high-end-model-for-low-complexity` 검토 후보를 만든다. 근거·예외 사유·누락 정보를 함께 표시하며 자동 모델 전환은 하지 않는다. 실제 실행 모델과 설정, 완료 기준, 검증 결과가 있으면 비교 가능한 세션군을 찾는다. 비교군은 저장소·작업 유형·위험·완료 기준이 다르면 분리한다.
3. 동등하거나 더 낮은 자원 설정에서 같은 완료 기준을 반복해 만족한 결과가 있고, 상위 설정이 더 나은 품질·안전·시간 결과를 보이지 않을 때 후보의 신뢰도를 높인다. 절감액은 당시 가격·과금 정책까지 확인한 경우에만 제시한다.
4. 후보는 “이 작업군에서 더 낮은 설정 A/B 비교를 실행”이라고 제안한다. “고성능 모델은 과하다” 또는 “비싼 모델이 나쁘다”라고 말하지 않는다.

시간·비용·품질은 서로 대체되지 않는다. 모델 A가 토큰을 적게 썼더라도 검증 누락, 실패 복구, 사람의 재작업, 위험 회피가 다르면 우세하다고 결론 내리지 않는다.

## 스킬과 지시 묶음 평가

스킬은 파일·설명·스크립트·도구 안내의 묶음이며, AGENTS.md와 작업 프롬프트도 실행 행동에 영향을 줄 수 있다. Eric Provencher의 「Rethinking skills and prompts for GPT-6 Astra」는 모델이 바뀔 때 이 지시들을 다시 검토하라고 권한다. 아래 해석은 2026-09-11 사용자가 제공한 원문 본문을 기준으로 한다. [원문 링크](https://x.com/pvncher/article/2095991462416490862)

저자는 스킬 설명의 과도한 범위·길이·충돌, 불필요한 사전 읽기와 재검증, 지나친 절차 강제가 맥락과 실행을 방해할 수 있다고 설명한다. 동시에 Astra에는 안전한 작업의 실행 권한과 완료 범위를 명확히 주는 것이 도움이 된다고 본다. 따라서 지시를 줄이는 것 자체를 목표로 삼지 않고 **필요한 맥락·권한·완료 기준을 작업과 모델에 맞게 제공했는지** 평가한다.

글은 실무 관찰과 권고다. 제공 본문에는 통제 실험·표본 수·효과 크기가 없으므로 특정 스킬이 Astra에 해롭거나 다른 모델에 유익하다고 확정하는 근거로 쓰지 않는다.

| 판정             | 필요한 근거                                                                                                          | 결과 표현                                  |
| ---------------- | -------------------------------------------------------------------------------------------------------------------- | ------------------------------------------ |
| 실행 확인        | 스킬 ID·버전 또는 hash, 활성화 시각, 실제 도구 호출/스크립트 결과                                                    | “스킬 vN 실행 관측”                        |
| 도움이 됨 후보   | 같은 유형·동일 완료 기준의 무스킬 또는 다른 버전 비교에서 검증 성공, 오류·재작업·시간 등의 일관된 개선               | “이 모델·작업군에서는 유지 후보”           |
| 부담 가능성 후보 | 스킬 로드 뒤 무관한 읽기·중복 명령·조기 중단·규칙 충돌이 관측되고, 비교군에서 같은 완료 기준을 더 적은 부담으로 만족 | “설명 축소 또는 적용 범위 축소를 A/B 검토” |
| 무관 또는 불충분 | 이름만 언급, 호출 결과 없음, 비교군 없음, 작업 결과 미확인                                                           | “효과 평가 불가”                           |

모델별 결과는 일반화하지 않는다. `model family + 모델 ID/버전 또는 alias + harness 버전 + skill ID/hash + skill 활성화 방식 + task cohort + 평가 버전` 조합에만 귀속한다. 다른 모델에 적용하려면 다시 비교한다.

### 원문에서 도출한 검토 후보

다음 ID는 설계 초안이며 실행 중인 규칙이 아니다. 정적 지시 검사에서 찾은 위험 신호와 실제 세션에서 관측한 영향을 분리한다. 긴 파일·많은 스킬·여러 번의 테스트만으로 후보를 확정하지 않는다.

| 초안 규칙 ID                  | 살펴볼 문제                                            | 필요한 관측 근거                                                         | 검토 방향·오탐 방지                                                                                                    |
| ----------------------------- | ------------------------------------------------------ | ------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------- |
| `skill-catalog-pressure`      | 스킬 설명이 과도하게 길거나 많아 선택 정보가 줄어듦    | 당시 노출된 스킬 목록·설명 길이, harness 버전, 실제 축약 여부            | 중복·미사용 후보를 검토한다. 설치 개수만으로 맥락 소모량이나 설명 축약을 단정하지 않는다.                              |
| `skill-trigger-overreach`     | 넓은 트리거·상충 설명 때문에 무관한 스킬 로드          | 당시 설명·트리거의 근거 발췌, 요청 범위, 실제 로드 기록                  | 예: 마이그레이션용 스킬이 모든 DB 작업에 활성화되는지 확인한다. 이름 언급을 실행으로 세지 않는다.                      |
| `skill-disclosure-mismatch`   | 필요한 분기 대신 모든 지침을 한꺼번에 읽음             | 루트 문서·참조 구조, 읽은 파일·범위, 수행한 작업 분기                    | 루트는 짧은 안내, 세부 절차는 필요할 때 읽도록 검토한다. 필수 의존성·안전 경계 읽기는 제외한다.                        |
| `instruction-overconstraint`  | 세부 절차나 충돌 지시가 현재 모델의 작업을 방해        | 실행 모델·추론 강도, 적용 지시 버전, 불필요한 단계·사용자 수정·중단 기록 | 모델별로 적용 범위나 강도를 비교한다. Sol·Luna에서 유효했던 지시를 Astra에도 유효하다고 가정하지 않는다.               |
| `unnecessary-context-loading` | 작은 수정마다 전체 문서·저장소를 선행 탐색             | 수정 범위, 읽기 호출과 지시의 연결, 실제 사용된 맥락                     | 작업별 읽기 범위를 검토한다. 정확성에 필요한 관련 코드 읽기까지 줄이라고 권하지 않는다.                                |
| `redundant-verification`      | 변경·실패·새 위험이 없는데 같은 검증을 반복            | 명령·결과·대상 revision, 그 사이 변경과 실패, 명시된 완료 기준           | 영향받은 검증 중심으로 범위를 검토한다. 실패 수정 후 재실행이나 필수 CI·운영 확인은 중복으로 분류하지 않는다.          |
| `avoidable-approval-stop`     | 이미 승인된 안전한 작업에서 불필요하게 재승인 요청     | 사용자 승인 범위, 실제 적용 경계, 중단 사유, 작업의 가역성·접근 권한     | 허용 범위를 구체화한다. 파괴적 작업·외부 전송·실제 권한 부족에 필요한 승인을 생략하라고 권하지 않는다.                 |
| `premature-handoff`           | 완료 기준에 실행·확인·수정이 있는데 초안만 넘기고 종료 | 사용자가 정한 완료 조건, 수행·미수행 단계, 차단 사유                     | 이어서 할 범위와 중단 조건을 명시한다. 사용자가 중간 리뷰를 요청했거나 외부 차단이 있으면 조기 종료로 단정하지 않는다. |

저자가 설명한 Codex의 스킬 설명 축약 동작과 모델별 경향은 **당시 harness·모델에 관한 주장**으로 기록한다. 다른 버전에도 같은 동작이 있는지는 별도로 확인한다. 정기 갱신에서는 새 글을 바로 규칙으로 활성화하지 않고 `출처 확인 → 검증 가능한 가설 → 반례·fixture → 모델별 보정 → 활성화` 순서를 따른다.

## 비교와 보정

관찰 세션은 배정이 무작위가 아니므로 인과 효과를 주장하지 않는다. Atlas는 다음 순서로 결과 강도를 표시한다.

| 수준     | 설계                                                          | 해석                                       |
| -------- | ------------------------------------------------------------- | ------------------------------------------ |
| 탐색     | 한 세션의 관측                                                | 다음 실험의 가설만 만든다.                 |
| 짝 비교  | 같은 저장소·완료 기준·위험도의 전후 또는 병렬 비교            | 차이를 기록하되 작업 난이도 차이를 남긴다. |
| 교차 A/B | 모델 또는 스킬 조건을 번갈아 배정하고, 독립적으로 결과를 검증 | 작업군 안에서만 유지·축소 후보로 쓴다.     |
| 재검증   | 다른 날짜·저장소 또는 모델 버전에서 같은 기준으로 반복        | 적용 범위를 넓힐 근거가 된다.              |

각 비교에는 대상 수, 제외 이유, 실패·중단 세션, 모델 응답 버전, 스킬 버전, 평가 규칙·프롬프트 버전, 기간을 남긴다. 성공 사례만 골라 평균을 내지 않는다. 샘플이 적거나 모델·가격·작업 조건이 바뀌면 결과는 `calibration-needed`로 되돌린다.

## 규칙 카탈로그와 수명주기

현재 규칙은 `packages/contracts/src/index.ts`의 코드 목록으로 관리하는 **결정적 규칙 카탈로그**다. 같은 입력과 활성 목록이면 같은 후보를 낸다. 외부 플러그인 실행이나 모델 기반 규칙 생성은 아직 없다.

| 단계 | 규칙 종류                     | 권한과 결과                                                                                                                                                           |
| ---- | ----------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 현재 | 버전 있는 순수 결정적 규칙    | 관측값·임계값·근거 ID를 가진 후보만 반환한다. 규칙 오류는 격리하고 `evaluation_failed`로 남긴다.                                                                      |
| 다음 | 검토된 규칙 플러그인 카탈로그 | manifest에 ID, 버전, 입력 계약, 적용 모델/작업 범위, 근거 요구, 테스트 fixture, 기본 상태, 소유자, 도입·검토일을 둔다. 네트워크·DB·AI 호출 없이 결정적으로 실행한다.  |
| 이후 | 모델 기반 후보 생성기         | 원문을 새로 수집하거나 최종 판정을 내리지 않는다. 반드시 근거 ID, 평가 모델 provenance, 프롬프트 버전, 신뢰 제한을 반환하고 결정적 검증 규칙 또는 사람 검토를 거친다. |

규칙의 상태는 `draft` → `calibrating` → `active` → `deprecated` → `retired`로 관리한다. `active` 전에는 합성 fixture에서 탐지 성공·정상 작업 오탐 방지·입력 부족·규칙 실패 격리를 확인하고, 대표 실제 세션에서 `candidate` 표현과 근거 연결을 검토한다. 임계값·입력·문구·모델 적용 범위가 바뀌면 버전을 올린다.

모든 결과에는 최소한 아래 식별자를 묶어 저장한다. 과거 결과를 새 카탈로그로 덮어쓰지 않는다.

```text
event schema + adapter/parser + evidence-selection policy
+ rule catalog (ID@version, enabled configuration)
+ evaluator prompt + judge model provenance + routing version
+ subject-model provenance + skill identity (when collected)
+ evaluation effective date and task cohort definition
```

재분석은 새 결과 레코드를 만들고 이전 결과의 적용일·규칙·근거 범위를 보존한다. 원본이 만료·마스킹·축약되어 비교 입력이 없으면 재분석 가능으로 표시하지 않는다.

## 운영 규칙

| 시점      | 할 일                                                            | 완료 조건                                                                                                                             |
| --------- | ---------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| 도입 전   | 적용 질문·대상 모델·작업군·필요 필드·반례를 명시                 | 실행 모델 등 필수 근거가 `unknown`이면 해당 후보를 만들지 않고, 비교군·비용 등 부가 근거 누락은 확신과 표현을 제한하는 테스트가 있다. |
| 도입      | effective date, 카탈로그 버전, 기본 상태, 담당자, fixture를 기록 | 결과에 버전과 근거 ID가 표시된다.                                                                                                     |
| 정기 검토 | 모델·harness·가격표·스킬·프롬프트 변경 또는 매 분기              | 최근 비교와 오탐·누락·보류율을 보고 유지·수정·중단을 결정한다.                                                                        |
| 보정      | 모델 alias가 다른 실제 모델로 해석되거나 비교군이 달라짐         | 기존 결과 범위를 좁히고 `calibration-needed`를 기록한다.                                                                              |
| 폐기      | 입력이 더 이상 수집되지 않거나 오탐·부담이 반복                  | 새 실행에서 비활성화하고 과거 결과와 버전은 읽기 전용으로 남긴다.                                                                     |

가격은 제공자·지역·계정·시간에 따라 달라질 수 있다. 비용 기준에는 출처 URL, 조회 시각, 통화·과금 단위, 입력·출력·캐시·추론 토큰 처리, 무료·구독·BYOK 여부를 함께 남긴다. 이 정보가 없으면 비용 대신 사용량만 표시한다.

## 최소 수집 보강 로드맵

아래는 설계 제안이며 현재 구현 완료 항목이 아니다. 지원하는 Source Adapter에서만 수집하고, 값의 출처를 `observed`, `user_declared`, `unknown`으로 표시한다. API 키·전체 환경변수·비밀 프롬프트·원문 스킬 내용을 기본 수집하지 않는다.

| 순서 | 추가할 최소 필드                                                                                                        | 해결하는 판단 공백                                      |
| ---- | ----------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------- |
| 1    | `subject_model`: provider, model ID/alias, model release/version, reasoning effort, harness version, observedAt, source | 실행 모델과 평가 모델을 분리하고 모델별 결과를 귀속     |
| 2    | `skill_execution`: skill ID, content hash/version, activation source, loaded/completed/failed, 연관 tool call ID        | 이름 언급과 실제 실행을 분리하고 버전별 A/B 가능        |
| 3    | `task_context`: 사용자 선택 작업 유형, 복잡도·위험 등급, 완료 기준, 변경 범위                                           | 간단한 작업과 고위험 작업을 같은 기준으로 비교하지 않음 |
| 4    | `outcome`: 검증 명령·상태, 리뷰/배포 상태, 실패·재작업 표지, 사람이 확인한 완료 여부                                    | 토큰·도구 수만으로 품질을 대체하지 않음                 |
| 5    | `cost_context`: 가격 출처·조회 시각·과금 단위·계정 유형. API 사용량은 모델별 분리                                       | 가격 추정을 막고 조건이 맞을 때만 비용 비교             |
| 6    | `evaluation_provenance`: prompt version, catalog manifest version, cohort definition, effective date                    | 결과를 같은 버전·조건에서만 재현·비교                   |

지시 효과 평가에는 추가로 `instruction_context`가 필요하다. 적용된 AGENTS.md·스킬·사용자 지시의 **출처·해시·적용 범위**, 노출된 스킬 목록과 설명 길이, 읽기·승인 요청·중단 이벤트와의 연결을 남기는 설계다. 파일 해시만으로 의미나 충돌은 판단할 수 없다. 그런 평가는 수집 정책에 따라 마스킹된 관련 발췌가 있을 때만 수행하고, 비밀 지시·전체 파일 본문을 기본 업로드하지 않는다. 토큰 수는 실제 계측값과 추정치를 구분하며, 가려진 시스템 지시나 미수집 맥락은 추측하지 않는다.

1–2단계는 기존 이벤트에 임의 문자열을 넣지 말고 공통 계약·Collector·서버를 함께 갱신한다. 3–5단계는 사용자가 명시적으로 입력하거나 신뢰 가능한 실행 메타데이터가 있을 때만 채운다. 첫 배포 전에는 합성 세션으로 `unknown` 보존, 모델 혼동 방지, 스킬 이름만 언급한 경우, 가격 정보 부재, 고위험 작업의 오탐 방지를 검증한다.
